# Подготовка данных продаж

**Степень свободы:** низкая в маппинге и проверках; средняя в выборе способа
чтения источников.

## Когда использовать

- новый набор CRM/Excel/CSV/JSON;
- новый период или `as_of_timestamp`;
- изменилась конфигурация клиента или mapping стадий/каналов;
- бизнес-навык сообщает, что обязательного поля или истории недостаточно.

## Не использовать

- для повторного чтения уже проверенного набора без изменений;
- для догадки о неизвестной колонке по смыслу — нераспознанное поле требует
  явного сопоставления;
- для подмены отсутствующей истории стадий текущим snapshot.

## Инструменты

1. Перед таблицами активируй `sys-excel`; для текстовых/служебных файлов используй
   встроенный `files`, для PDF — `sys-pdf`, DOCX — `sys-word`.
2. Для корпоративных источников используй `sys-search`/`sys-retrieval` или
   подключённый коннектор, а не память модели.
3. `python_run` допустим только для численных/структурных проверок после чтения
   данных системным инструментом; не используй его как файловый менеджер.

## Рабочий процесс

Скопируй и веди прогресс для многошаговой подготовки:

- [ ] Зафиксирован режим: демо / пилот / промышленный.
- [ ] Зафиксированы `reporting_period`, `as_of_timestamp`, часовой пояс и валюта.
- [ ] Определены источники и их версии/даты выгрузки.
- [ ] Поля сопоставлены с канонической моделью без семантической догадки.
- [ ] Проверены обязательные поля, типы, дубликаты, временные границы.
- [ ] Для ретроспективы проверена история стадий и исключены события после as-of.
- [ ] Сформирован список критических и некритических пробелов.

## Канонические правила

- История этапов (`Stage_History`) обязательна для исторической воронки.
- Не смешивай разные версии плана, mapping и конфигурации без явного выбора.
- Будущие события относительно `as_of_timestamp` исключай и сообщай их количество.
- В пилоте и промышленном режиме недоступный источник = пробел/необходимость
  интеграции, а не synthetic fallback.

## Выход

Верни: `data_status`, `reporting_period`, `as_of_timestamp`, `source_register`,
`canonical_mapping`, `quality_checks`, `missing_required`, `source_conflicts`,
`leakage_prevented`, `ready_for_skills` и ссылки на доказательства.

## Исполнение нормализации

Для детерминированного маппинга прочитай код из `Референсы/normalize.py` и передай его в `python_run`.

Если профиль содержит `inherits`, передай в `build_mapping` реестр профилей через `profile_registry`. Для файлов `Референсы/amocrm.json`, `Референсы/bitrix24.json` родитель — `Референсы/generic.json`. Используй `build_profile_registry(generic_profile, amocrm_profile, bitrix24_profile)`. Если родитель не передан или цикл наследования некорректен, функция **не падает**, а возвращает диагностический статус `profile_parent_required`.

Эталонный вызов:

```text
registry = build_profile_registry(generic_profile, amocrm_profile, bitrix24_profile)
normalized, result = normalize_dataframe(df, "Leads", amocrm_profile, registry)
```

Не вызывай наследуемый CRM-профиль без реестра и не разрешай `inherits` через LLM-маппинг.

## Ресурсы навыка

Дополнительные материалы вынесены в подпапку `Референсы/`:
- `Референсы/normalize.py` — детерминированный маппинг CRM-полей;
- `Референсы/ИНТЕГРАЦИЯ_CRM.md` — интеграция CRM и история стадий;
- `Референсы/МОДЕЛЬ_ДАННЫХ.md` — канонический контракт данных;
- `Референсы/ПРОТОКОЛ_НОРМАЛИЗАЦИИ.md` — протокол нормализации CRM;
- `Референсы/ФОРМАТ_ПИЛОТА.md` — формат пилота без интеграций;
- `Референсы/generic.json`, `Референсы/amocrm.json`, `Референсы/bitrix24.json` — профили канонических алиасов;
- `Референсы/КОНФИГУРАЦИЯ_КЛИЕНТА.yaml` — конфигурация клиента;
- `Референсы/ОЖИДАЕМЫЙ_ДЕМО_РЕЗУЛЬТАТ.json`, `Референсы/ОЖИДАЕМЫЙ_LLM_EVIDENCE.json` — эталонные результаты для валидации;
- `Референсы/Демо_*.csv` — демо-данные (18 файлов);
- `Референсы/Шаблон_*.csv` — шаблоны клиентских выгрузок (16 файлов).

Подгружай файл из `Референсы/` только когда он нужен для текущего шага.
