Навык преобразует описание задачи, требования пользователя или черновик в структурированное, готовое к использованию описание AI-скилла для платформы GigaChat Enterprise.

Навык гарантирует, что каждый сформулированный скилл:

следует Core Principles платформы (todo-обязательность, цикл действие→проверка→апдейт, проверка кодом, источник или «не нашёл», вопросы через question);
использует правильные инструменты для каждой задачи (системные скилы vs python_run);
содержит чёткие границы ответственности агента;
определяет критерии качества и пограничные случаи;
готов к немедленному внедрению в платформу.
Когда использовать
Используй этот навык, если пользователь просит:

создать новый скилл для платформы;
переформулировать задачу в формат скилла;
улучшить существующее описание скилла;
проверить скилл на соответствие Core Principles;
подготовить документацию для AI-агента;
стандартизировать описание навыка по шаблону платформы.
Входные данные
Входом может быть:

текстовое описание задачи от пользователя;
черновик скилла;
существующий скилл для рефакторинга;
требования к агенту;
примеры работы агента;
ошибки предыдущей версии скилла;
устные или неполные формулировки.
Если входные данные неполные, не выдумывай недостающие факты. Отмечай их как не указано или требует уточнения.

Главный принцип
Не улучшай скилл за пользователя преждевременно.

Сначала зафиксируй:

что пользователь явно сказал;
что можно аккуратно вывести из контекста;
что остаётся неопределённым;
что нужно уточнить перед финализацией скилла.
Всегда отделяй:

Факт → Гипотеза → Неопределённость → Вопрос на уточнение
Алгоритм работы
Шаг 1. Восстановить суть скилла
Определи, какую задачу должен решать скилл.

Сформулируй кратко:

Скилл [название] позволяет агенту [действие] на основе [входные данные], чтобы получить [результат].
Пример:

Скилл "Работа с Excel" позволяет агенту анализировать табличные данные (.xlsx/.csv/.parquet) через pandas-операции, чтобы выдавать сводки, агрегации и визуализации без ручного копирования чисел.
Шаг 2. Определить триггеры активации
Зафиксируй, когда агент должен активировать этот скилл.

Примеры триггеров:

пользователь просит прочитать/создать файл определённого формата;
задача требует специализированного инструмента;
обнаружен файл известного типа;
пользователь явно называет скилл.
Формат:

Триггеры активации:
1. Пользователь просит "прочитать .docx" → активировать sys-word
2. Задача требует анализа .xlsx → активировать sys-excel
3. Пользователь говорит "найди в документах" → активировать sys-search
Шаг 3. Сопоставить инструменты задачам
Для каждой подзадачи скилла укажи правильный инструмент.

Используй матрицу выбора инструмента:

Задача	Скил	Тул
Текстовые файлы (.txt/.md/.json/.csv/.log)	sys-files	files(op=…)
Картинки (.png/.jpg/.jpeg/.gif/.webp до 5 MB)	sys-files	files(op="read")
Word .docx	sys-word	word(op="read"|"write")
Excel/CSV/Parquet/JSON/TSV	sys-excel	excel(op="probe"|"read"|"write"|"query")
PowerPoint .pptx	sys-powerpoint	powerpoint(op="read"|"write"|"query")
PDF	sys-pdf	pdf(op="read"|"info"|"render")
BM25 поиск по файлам	sys-search	search(op="query"|"reindex")
Семантический RAG по KB	sys-retrieval	retrieval(op="search"|"list")
Численные вычисления/графики/ML	—	python_run
Запреты:

❌ python_run для простого текстового I/O
❌ python_run для удаления файлов (только files(op="delete"))
❌ python_run когда есть системный скил
Шаг 4. Описать входные данные
Собери список входных данных скилла.

Для каждого входа укажи:

название;
формат;
обязательность;
пример;
риски качества.
Пример:

1. Путь к файлу
   Формат: строка (относительный путь)
   Обязательность: обязательно
   Риски: абсолютный путь вместо относительного, путь с префиксом /session/
Шаг 5. Описать ожидаемый результат
Зафиксируй, что скилл должен выдать.

Укажи:

формат результата;
обязательные поля;
нужен ли файл в session;
нужен ли markdown-отчёт;
нужны ли цитаты с источниками.
Пример:

Ожидаемый результат:
- markdown-таблица с данными;
- ссылки на источники (файл:строка);
- файл .xlsx в session при запросе на генерацию.
Шаг 6. Зафиксировать границы ответственности
Определи, что скилл может делать сам, а что нет.

Скилл может:
- активировать нужный инструмент;
- валидировать входные параметры;
- форматировать вывод по шаблону;
- цитировать источники.

Скилл не должен:
- выдумывать содержимое файлов;
- скрывать неопределённость;
- использовать python_run вместо системного скилла;
- писать план в тексте вместо todo.
Шаг 7. Встроить Core Principles
Гарантируй, что скилл следует принципам платформы:

1. todo-обязательность

Перед любой работой скилл формирует план через todo — даже если один шаг.
2. Цикл действие→проверка→апдейт

После каждого тула: проверка результата → апдейт плана → следующее действие.
3. Проверка кодом

Не пересказывать "что должно получиться" — запустить тул и показать результат.
4. Источник или «не нашёл»

Любой факт опирается на артефакт, прочитанный в этой сессии.
Нет источника → «в доступных источниках не нашёл».
5. Вопросы через question

Не inline-вопросы в конце ответа.
question только при ambiguity (2+ интерпретации, missing ключевая сущность).
Шаг 8. Определить пограничные случаи
Выдели кейсы, на которых скилл может ошибаться:

файл не найден;
формат не распознан;
данные противоречивы;
контекст слишком длинный;
инструмент вернул ошибку;
пользователь передал абсолютный путь;
workspace не прикреплён;
KB не индексирована.
Для каждого кейса укажи стратегию обработки.

Шаг 9. Зафиксировать критерии качества
Раздели критерии на категории:

Корректность:
- правильный инструмент выбран;
- данные не выдуманы;
- цитаты с источниками.

Полнота:
- все подзадачи покрыты;
- неопределённости явно названы.

Формат:
- вывод соответствует шаблону;
- файлы лежат в session;
- пути относительные.

Критические ошибки:
- python_run вместо sys-files для чтения .txt;
- план в тексте вместо todo;
- inline-вопросы пользователю;
- выдуманные id/цитаты.

Правила качества
Хороший скилл должен быть:

однозначным — нет двусмысленных формулировок;
полным — покрыты все подзадачи и пограничные случаи;
согласованным с платформой — следует Core Principles;
пригодным к внедрению — можно сразу активировать и использовать;
честным — неопределённости явно названы;
тестируемым — критерии качества позволяют построить evals.
Запреты
Не делай следующее:

❌ не выдумывай инструменты, которых нет в платформе;
❌ не игнорируй матрицу выбора инструмента (sys-* vs python_run);
❌ не пропускай раздел Core Principles;
❌ не смешивай описание скилла с его исполнением;
❌ не создавай скилл без триггеров активации;
❌ не оставляй «не указано» в обязательных полях без комментария;
❌ не пиши skill_description без примеров использования.
