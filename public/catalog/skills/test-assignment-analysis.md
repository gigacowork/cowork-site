# Анализ тестового задания кандидата

## Когда использовать (триггеры)

- Пользователь даёт ссылку на GitHub/GitLab-репозиторий с тестовым заданием кандидата и просит его оценить — например «оцени тестовое», «посмотри репозиторий кандидата», «поставь балл за тестовое задание».
- Нужно проверить, соответствует ли решение условию кейса, и получить балл 0–10 с обоснованием по рубрике.
- Часть процесса отбора кандидатов — тогда навык применяется к одному кандидату за раз, его по очереди вызывает отдельный оркестрирующий процесс; так же он работает и как самостоятельный запрос по одной ссылке.

Наличие тестового задания на GitHub/GitLab — требование процесса найма, а не то, что этот навык проверяет или решает сам: он честно оценивает то, что реально находит по ссылке, или прямо говорит, что там ничего нет.

Анти-триггеры (когда не применять):

- Ссылки на тестовое в резюме нет — не искать её по нику или названию проекта, а зафиксировать `test_link_missing: true`, балл 0, дальше анализ не запускается.
- Нужна оценка всего пула кандидатов целиком или их ранжирование между собой — это отдельная задача агрегации, не эта.
- Нужно только проверить, что ссылка открывается, без полной оценки по рубрике — достаточно простой проверки доступности, полная рубрика не нужна.

## Степень свободы

Средняя: правила «ссылка только из резюме», обработка отсутствующей/сломанной ссылки, запрет на исключение критериев из взвешенной суммы и шкала 0–10 — жёсткие; глубина чтения кода, формулировки обоснований и корректировка весов рубрики (с согласованием, под конкретную вакансию) — на суждение агента.

## Веб-доступ к репозиторию

Этот навык по своей сути требует открывать внешние ссылки (репозитории GitHub/GitLab, задеплоенные стенды) — это HTTP-доступ в публичный интернет.

Если инструменты `web` (поиск по интернету) и `webfetch` (чтение страницы по URL) доступны в сессии — URL уже известен из резюме, поэтому открывать сразу через `webfetch(url)`, без промежуточного `web`-поиска. `web` нужен только для поиска ещё неизвестного URL — но этот навык никогда не ищет и не угадывает репозиторий по имени/нику кандидата (см. «Если ссылки нет» ниже), поэтому в штатной работе используется только `webfetch`.

Если веб-инструменты недоступны в текущей сессии — не имитировать вызов и не притворяться, что страница была открыта. Полноценная проверка тестового в этом случае технически невозможна: выставить `code_not_read: true` и `test_link_unverified: true` с причиной «инструменты веб-доступа недоступны в сессии — не ссылка недоступна, а нет канала для её проверки», и эскалировать вопрос вызывающему процессу/пользователю — предложить активировать веб-инструменты или явно принять ограниченную оценку. То, что описано в резюме текстом (без кода), можно учесть только с явной пометкой «ориентир по знаниям модели, не проверен по открытым источникам» — не как подтверждённый факт о решении. Никогда не писать «интернета нет» как безусловный факт окружения агента — это ограничение конкретной сессии, а не платформы.

## Если ссылки нет

- Выставить `test_link_missing: true`, `балл_тестового: 0`.
- Никогда не оценивать тестовое по одному лишь описанию в резюме.
- Никогда не угадывать репозиторий по имени/нику кандидата — использовать только явно указанную ссылку.

## Если ссылка есть

- Открыть репозиторий инструментом `webfetch` (URL уже известен из резюме — открывать сразу, без `web`-поиска; см. «Веб-доступ к репозиторию» выше), прочитать код и README целиком.
- **README — источник контекста, а не подтверждение фактов.** Обоснование по критериям «Архитектура и качество кода», «Покрытие тестами», «Соответствие заявленного в резюме стека фактическому коду» должно опираться на реально прочитанные файлы (список модулей/директорий, ключевые классы или функции, зависимости из `package.json`/`pom.xml`/`requirements.txt` и т.п.) — не на текст README. Если README и код расходятся (например, README называет решение «mock», а в коде — рабочие интеграции с внешними сервисами, или наоборот) — доверять коду и отдельно отметить расхождение как риск/находку. В пределах одного вызова достаточно открыть манифест зависимостей, структуру каталогов и 2–4 ключевых файла, а не вычитывать весь репозиторий построчно.
- Если в резюме, помимо ссылки на репозиторий, указан задеплоенный стенд/демо — открыть и его в любом случае, даже если репозиторий недоступен. Работающий стенд — самостоятельный источник фактов о решении (реальный стек, функциональность, интерфейс) и не подменяется описанием из README или из тестового другого кандидата.
- **Прежде чем пометить ссылку как недоступную — попробовать минимум два разных способа доступа** (например: прямой запрос, затем повторная попытка тем же способом или другим — прямая ссылка на файл вместо API, зеркало, указанный в резюме стенд вместо репозитория; для GitLab/self-hosted и файлообменников — прямой запрос, затем повтор с другим URL/протоколом). Балл за тестовое весит значительную долю итога — ошибочное «недоступно» из-за одного неудачного запроса обнуляет кандидата незаслуженно.
  - **Если у кандидата несколько ссылок на тестовое (например, два разных репозитория, или репозиторий и отдельно стенд) — правило двух попыток применяется к КАЖДОЙ ссылке отдельно, а не один раз на кандидата в целом.** Неудача по одной ссылке (даже подтверждённая) не переносится на другую и не освобождает от её отдельной проверки. Пока не проверена (двумя способами) каждая указанная ссылка — рано выставлять `test_link_broken` кандидату целиком: достаточно, чтобы хотя бы одна ссылка оказалась рабочей, чтобы не обнулять тестовое.
    - *Пример ошибки, которую это правило запрещает:* в резюме — ссылка A (подтверждён 404) и ссылка B (не открывалась отдельно). Нельзя пометить обе как недоступные и обнулить кандидата на основании одной проверенной A. Правильно: открыть B минимум двумя способами так же, как A, и только если ОБЕ ссылки независимо и подтверждённо недоступны — ставить `test_link_broken: true` кандидату.
  - **Временный отказ (429 rate-limit, таймаут, 5xx) — это не подтверждение недоступности.** Если оба независимых захода дали именно временный отказ, а не определённый негативный ответ (404, приватность, «репозиторий удалён») — не выставлять `test_link_broken`. Вместо этого зафиксировать `test_link_unverified: true` с описанием, чем именно закончились обе попытки, оценить то, что удалось увидеть косвенно (задеплоенный стенд, если есть; сохранённый в резюме текст описания решения — с явной пометкой «не подтверждено кодом»), и передать дальше как открытый вопрос, а не как обнулённого кандидата.
  - Только если оба способа независимо подтвердили определённую недоступность (404, приватность, удаление) — считать репозиторий сломанным и выставлять `test_link_broken: true`, `балл_тестового: 0`, не домысливать содержимое.
- Репозиторий может быть на GitHub, GitLab или self-hosted — способ доступа не важен, важно прочесть код.
- Если у кандидата несколько ссылок и полная двухпопыточная проверка каждой (плюс чтение кода) не укладывается в один вызов инструмента — растянуть проверку этого кандидата на несколько последовательных вызовов, а не обрезать проверку раньше времени и не переходить к следующему кандидату, пока не закрыты все ссылки текущего.

## Если код не удалось прочитать по файлам (открыта только структура/README)

Бывает, что первая попытка даёт доступ только к структуре каталогов или README, а не к содержимому ключевых файлов (манифест зависимостей, реализация). Это не то же самое, что полноценная проверка, и не повод сразу выставлять обычный балл «как если бы код был прочитан».

- **Повторить попытку** открыть хотя бы 2–4 ключевых файла (манифест зависимостей + один-два файла с реализацией), прежде чем формулировать балл — не останавливаться на первой неудаче так же, как и для доступности ссылки.
- Если и повторная попытка не дала содержимого файлов — критерии «Архитектура и качество кода» и «Покрытие тестами» **не оцениваются как обычно и не получают балл на основании структуры или README**: занизить их по умолчанию (аналогично `wrong_track` — явно пониженный балл, вплоть до 0, с пометкой причины), а не подставлять правдоподобную оценку «по структуре репозитория».
- Выставить флаг низкой уверенности `code_not_read: true` и явно вынести его в статус/риски кандидата — это должно быть видно в отчёте, а не теряться в обычной строке таблицы наравне с кандидатами, чьё решение было прочитано полностью.
- **Никогда не писать в обосновании формулировки вроде «оценено по структуре репозитория, код не читался построчно» и одновременно выставлять балл так, будто содержимое было прочитано** — такое обоснование само себе противоречит и обесценивает балл. Если признание «код не читался» появилось в тексте — это сигнал пересчитать соответствующие критерии по правилу выше, а не просто оставить как есть.

## Если сдан артефакт не того типа или не того трека

Ссылка открывается, но то, что по ней лежит, не отвечает на условие тестового задания вакансии — например, текстовый документ вместо кода на кодовой вакансии, или рабочее решение другой специализации (backend-сервис на Frontend-вакансии, DS-пайплайн там, где нужен веб-интерфейс).

- Это не `test_link_missing` и не `test_link_broken` — ссылка рабочая, просто содержимое не то. Выставить `wrong_track: true` с кратким описанием, что именно сдано вместо требуемого.
- Балл **0** по всем критериям рубрики, которые по определению нельзя оценить на несоответствующем артефакте (для кодовой вакансии это, как правило, архитектура и качество кода, покрытие тестами, реальная работоспособность применительно к требуемому стеку). Эти критерии не пропускаются и не исключаются из взвешенной суммы — у них явный балл 0 (см. правило нормировки ниже).
- Если в сданном артефакте есть содержательное пересечение с условием (например, документ по бизнес-процессу закрывает часть аналитической составляющей кейса) — оценить по существу только эту пересекающуюся часть в рамках подходящего критерия, с явным обоснованием; остальные критерии — по-прежнему 0.

**Если кандидат явно подписал несколько ссылок под разные задачи/кейсы/треки** (например, «тестовое кейса А» и отдельно «тестовое кейса Б», или «бэкенд-часть» и «фронтенд-часть» одного кейса) — `wrong_track`/`wrong_track_partial` ставится только по итогам проверки ссылки, относящейся именно к текущему прогону (вакансии/кейсу, для которого сейчас идёт отбор), а не по факту, что среди прочих ссылок кандидата есть артефакт другого трека. Наличие у кандидата репозитория не того трека рядом с релевантным — это не основание занижать релевантную ссылку; если релевантная ссылка по содержимому соответствует вакансии — она оценивается как обычная, полноценная. *Пример:* кандидат подписал три ссылки под три конкретные задачи двух разных кейсов (бэкенд кейса 1, фронтенд кейса 1, фронтенд кейса 2); при отборе фронтенд-разработчиков оценивается фронтенд-ссылка(и), и то, что среди прочих есть ссылка на бэкенд — не повод ставить `wrong_track_partial` на фронтенд-решение.

## Рубрика оценки

0–10 по каждому критерию, с обоснованием 1–2 предложения. Рубрика по умолчанию (скорректировать и согласовать с пользователем **под критерии конкретной вакансии до начала прогона** — не использовать универсальный набор ниже как есть для профильной роли, например Frontend или Data Science, у которых есть специфичные измеримые критерии: работа с UI/состоянием/API, качество данных и метрик и т.п.):

- Соответствие условию кейса — решает именно то, что просили, а не что-то смежное
- Архитектура и качество кода
- Покрытие тестами
- Документация
- Реальная работоспособность / работающий деплой
- Соответствие заявленного в резюме стека фактическому коду

**Правило нормировки взвешенной суммы — критично:** сумма весов рубрики всегда равна 100%, и балл считается по полному набору критериев. Критерий, который нельзя оценить по факту (нет кода — `wrong_track`, часть решения недоступна) получает **0**, а не исключается из знаменателя. Никогда не пересчитывать сумму на суженный набор фактически оценённых критериев (например, `(6×0.3 + 7×0.3) / 0.6` вместо `(6×0.3 + 7×0.3 + 0×0.4) / 1.0`) — такая перенормировка систематически завышает балл кандидатам с неполным или не тем решением, вплоть до того, что артефакт без единой строки кода набирает больше баллов, чем работающее решение с частично недоступным репозиторием.

Взвешенная сумма (по умолчанию — равные веса, можно скорректировать; если работающий функционал критичен для вакансии — предложить повысить его вес) → `балл_тестового` на шкале 0–10.

**Пример проверенной рубрики для нетехнической роли (бизнес-аналитик)**, где артефакт — не код, а документ/схема: Требования (ТЗ/User Story/Use Case) — 25%, Моделирование (BPMN/UML) — 20%, Работа с данными (SQL/Excel/BI) — 20%, Работа со стейкхолдерами — 15%, Инструменты — 10%, Agile/Scrum — 10%. Это не жёсткий стандарт, а рабочий образец: для новой нетехнической роли отталкиваться от него и адаптировать состав/веса под вакансию, а не собирать с нуля.

## Если тестовое используется как бонус, а не как отсекающий критерий

Иногда итоговая формула по вакансии устроена так, что тестовое не должно понижать итоговый балл кандидата (например, для ролей, где отсутствие технического тестового не считается недостатком) — сама формула агрегации при этом меняется отдельно, вне этого шага.

- **Это правило только про формулу агрегации, а не про то, нужно ли вообще оценивать тестовое.** Если ссылка есть и открывается — тестовое оценивается по полной рубрике точно так же, как в стандартной схеме, с тем же качеством проверки (чтение кода, минимум две попытки при недоступности и т.д.).
- Пропустить оценку допустимо **только** по тем же основаниям, что и всегда: ссылки нет (`test_link_missing`) или её недоступность подтверждена двумя независимыми способами (`test_link_broken`) — не потому, что «результат всё равно не понизит балл, можно не проверять». Экономия усилий на этом шаге лишает кандидата шанса на бонус, который мог бы поднять его в топ-N, даже если формально никого не штрафует.

## Вывод

- Ссылка(и), флаги `test_link_missing` / `test_link_broken` / `test_link_unverified` / `wrong_track` / `code_not_read`
- Баллы по каждому критерию с обоснованием — каждое техническое утверждение (файл, технология, метрика) должно быть прослеживаемо до ссылки именно этого кандидата, а не соседнего по списку
- `балл_тестового` (0–10)
- Ключевые риски

## Пограничные случаи

- **В репозитории только README без кода** — это факт для критерия «качество кода» (близкий к 0), а не повод домысливать реализацию по описанию.
- **Репозиторий содержит чужое/скопированное решение** — зафиксировать как риск, снизить балл по критериям качества с обоснованием.
- **Ссылка ведёт на ветку/файл, а не на корень репозитория** — оценивать содержимое по указанной ссылке, при необходимости открыть корень для контекста.
- **Задеплоенный стенд не открывается** — это минус по «реальной работоспособности», а не `test_link_broken` (флаг — только для самого репозитория).
- **Репозиторий недоступен, но задеплоенный стенд из резюме открывается** — не ставить `test_link_broken` с баллом 0 автоматически: сначала оценить то, что видно через стенд (функциональность, интерфейс, фактически используемые технологии — по структуре страницы/сетевым запросам, если инструменты это позволяют), затем честно занизить критерии, которые требуют исходного кода (архитектура, покрытие тестами) — с явной пометкой «код недоступен, оценено по работающему стенду».
- **При параллельной проверке нескольких кандидатов** — перед тем как включить в обоснование конкретную техническую деталь (имя файла, компонент, технологию), свериться, что она взята именно из источника проверяемого кандидата, а не перепутана со страницей репозитория, открытой для другого кандидата в том же прогоне.

## Важно

- Никогда не оценивать «на глаз» по описанию в резюме или по README — только по реально прочитанному коду.
- **Не помечать ссылку как недоступную после одной неудачной попытки, и не путать временный отказ платформы (429/таймаут) с подтверждённой недоступностью** — цена такой ошибки велика для кандидата; перепроверить другим способом перед обнулением (см. «Если ссылка есть»).
- **Если ссылок несколько — правило двух попыток применяется к каждой отдельно; недоступность одной ссылки не распространяется на остальные.**
- **Если код не был прочитан по файлам (только структура/README) — это не полноценная оценка**: занизить кодовые критерии по умолчанию и явно пометить `code_not_read: true`, а не выставлять обычный балл с оговоркой в тексте.
- **Формула «тестовое — бонус» меняет только агрегацию, не отменяет саму оценку** — тестовое с рабочей ссылкой оценивается всегда, пропуск допустим только при `test_link_missing`/`test_link_broken`.
- Отсутствующая/недоступная ссылка, подтверждённая минимум двумя способами проверки — нормальный, не ошибочный исход: фиксировать спокойно с баллом 0, без домыслов.
- Артефакт не того трека — это `wrong_track` с баллом 0 по кодовым критериям, а не частично оценённое тестовое с перенормированной суммой.
- Взвешенная сумма всегда считается по полному набору критериев (сумма весов = 100%) — неоценённый критерий получает 0, никогда не исключается из знаменателя.
- Баллы всегда сопровождать обоснованием, не выдавать голые цифры.
- Не оценивать по скриншотам/презентациям вместо кода.
- Веб-доступ — открывать репозиторий инструментом `webfetch` по известному URL из резюме, без предварительного `web`-поиска. Если `web`/`webfetch` не активированы в сессии — см. «Веб-доступ к репозиторию» выше: эскалировать вопрос вызывающему процессу, не имитировать чтение и не подменять код знаниями модели без явной пометки.
